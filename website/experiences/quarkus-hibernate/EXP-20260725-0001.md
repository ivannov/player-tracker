## 1. Objective
Map a `@ManyToOne` relationship (e.g. a `Match` entity's `homeTeam` field pointing to `Team`) to the correct foreign-key column defined in a Flyway migration (e.g. `home_team_id`).

## 2. The Trap
Hibernate does not convert multi-word camelCase Java field names to snake_case for FK column names the way it does for simple single-word fields. Leaving `@JoinColumn` off a field like `homeTeam` makes Hibernate default to generating `homeTeam_id` instead of the migration's `home_team_id`. This fails at startup with a schema validation error (`Schema-validation: missing column [home_team_id]`), or silently creates the wrong column if `clean-at-start`/`generate-ddl` masks it.

## 3. Abstracted Insight
> **Core Principle:** Any `@ManyToOne` (or other FK-bearing) field whose Java name has more than one word MUST carry an explicit `@JoinColumn(name = "snake_case_col")` — never rely on Hibernate's implicit naming strategy for multi-word FK fields.

## 4. Validated Path
```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "home_team_id")
public Team homeTeam;

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "away_team_id")
public Team awayTeam;
```
Cross-check the column name against the exact name used in the corresponding `V1__create_*.sql` migration before running the app.

## 5. Verification Checklist
- [ ] Every multi-word `@ManyToOne`/`@OneToOne` field has an explicit `@JoinColumn(name = ...)`.
- [ ] The `name` value matches the FK column name in the Flyway migration exactly (snake_case).
- [ ] App starts cleanly against a fresh `clean-at-start` dev DB with no schema-validation errors.
