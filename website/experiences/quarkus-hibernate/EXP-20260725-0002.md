## 1. Objective
Declare a text/`VARCHAR` column on both sides — the JPA entity (`@Column`) and the Flyway migration DDL — so Hibernate's startup schema validation passes.

## 2. The Trap
Hibernate's schema validator compares the declared `@Column(length = N)` against the actual DB column's `VARCHAR(N)` length. If the migration says `logo_url VARCHAR(512)` but the entity field omits `length` (defaulting to Hibernate's implicit 255) or sets a different number, the app fails at startup with a schema-validation mismatch on that column.

## 3. Abstracted Insight
> **Core Principle:** Every `@Column` backing a `VARCHAR(N)` migration column must set `length = N` explicitly — never leave it to the default, and always update both sides together when changing a column's size.

## 4. Validated Path
```sql
-- V1__create_teams.sql
logo_url VARCHAR(512)
```
```java
@Column(name = "logo_url", length = 512)
public String logoUrl;
```
When resizing a column, grep both the migration file and the entity field in the same change so they never drift apart.

## 5. Verification Checklist
- [ ] `@Column(length = N)` value equals the `VARCHAR(N)` in the migration for every text column touched.
- [ ] App starts cleanly against a fresh `clean-at-start` dev DB with no schema-validation errors for the entity.
