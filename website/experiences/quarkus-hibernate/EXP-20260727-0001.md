## 1. Objective
Write a teardown/cleanup block that deletes test fixture rows across several FK-related tables (e.g. Team -> TeamFormation -> Participation -> Match) inside one QuarkusTransaction.requiringNew() block, without intermittent foreign key violations.

## 2. The Trap
Panache's deleteById() loads the entity and calls EntityManager.remove() on it -- a managed removal deferred to the next flush -- while Entity.delete("where clause", params) issues an immediate bulk HQL DELETE via executeUpdate(). Hibernate auto-flushes pending changes before a query only for query spaces (tables) it judges the query overlaps; this heuristic does not reliably recognize that a bulk delete against a referencing table (e.g. team_formations) depends on a still-unflushed deleteById() removal of a referenced row (e.g. a participations row). The result is intermittent 'foreign key violation' errors -- observed to pass or fail nondeterministically across otherwise-identical isolated single-test runs against a fresh Testcontainers Postgres, with no code change between runs. When the transaction rolls back on this exception, every delete in that same requiringNew() block (including ones earlier in program order that appeared to succeed) is undone, silently leaking fixture rows into later tests and causing further unrelated-looking failures (e.g. team/player resolution finding a stale aliased row from a previous, supposedly-cleaned-up test).

## 3. Abstracted Insight
> **Core Principle:** Within one transaction, never rely on delete ordering across a mix of deleteById() (managed remove, deferred) and bulk delete() (immediate) when later statements have an FK dependency on earlier ones. Pick one style and use it consistently for every delete in the block.

## 4. Validated Path
Rewrite every delete in the teardown as a bulk HQL delete: Entity.delete("id = ?1", id) or Entity.delete("id in ?1", ids) instead of Entity.deleteById(id). Bulk deletes execute immediately as real SQL statements in the exact order written, so FK-dependency ordering (children before parents) is guaranteed within the same transaction. Order the calls child-to-parent (e.g. PlayerAppearance/MatchEvent -> Match -> Participation -> TeamFormation -> Team -> Competition) exactly as the schema's FK graph requires.

## 5. Verification Checklist
- [ ] In a QuarkusTransaction.requiringNew() cleanup block deleting across multiple FK-related tables, use bulk .delete("id = ?1"/"id in ?1", ...) for every entity, never deleteById(), and order the calls from dependent (child) tables to referenced (parent) tables.
