## 1. Objective
Implement AmbiguityInboxService.confirmNewPlayer (LT-009.02): create a brand-new Player for an ambiguity review, then reuse PlayerMatchingService.writeAlias to write the player_aliases row exactly like the auto-resolve path does.

## 2. The Trap
writeAlias runs its own QuarkusTransaction.requiringNew() internally (a separate DB transaction) so it can catch a concurrent unique-constraint race independently of the caller. That's safe when the Player argument already exists as a previously-committed row (the auto-resolve path always looks up an existing player). But if the caller creates the Player in its own still-open ambient @Transactional method and passes it straight into writeAlias, the nested transaction's FK insert into player_aliases references a player_id that hasn't committed yet from its transaction's point of view -- it either blocks on the uncommitted row's lock or fails the FK check, depending on isolation, because REQUIRES_NEW is a genuinely separate database transaction, not just a savepoint.

## 3. Abstracted Insight
> **Core Principle:** A REQUIRES_NEW method call is a real transaction boundary: anything it references via FK must already be committed in a transaction that finished before the REQUIRES_NEW transaction begins. Don't reason about entity attach/detach state here (that's the EXP-20260726-0001 trap) -- reason about commit order in wall-clock terms. If you create a row and then call a REQUIRES_NEW-based writer with it in the same operation, the row's own creation must be committed (its own QuarkusTransaction.requiringNew() block that returns) strictly before the writer call, not merely persisted within an ambient transaction still in flight.

## 4. Validated Path
In AmbiguityInboxService.confirmNewPlayer, split the operation into three sequential, independently-committing QuarkusTransaction.requiringNew() calls: (1) read the review's rawName/teamId/source, (2) create and persist the new Player alone and let that transaction commit before returning its id, (3) only then call playerMatchingService.writeAlias(...) (which opens its own nested transaction against the now-committed player), followed by a final requiringNew() block to mark the review RESOLVED. Contrast with resolveReview (picking an existing player), which is safely a single @Transactional method because the chosen player was already committed long before this call.

## 5. Verification Checklist
- [ ] Before wrapping a create-then-write-dependent-row sequence in one @Transactional method, check whether the 'write dependent row' step internally opens its own QuarkusTransaction.requiringNew() -- if so, the created row must be committed in a prior, already-finished transaction, not just persisted in the ambient one
