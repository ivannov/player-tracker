title: 'Extracting a reusable resolution service from an inline resource: keep detached
  entities out of a separately-transactional bean'
description: When extracting inline alias/ambiguity-queueing logic (e.g. ParticipationImportResource's
  recordTeamAlias) into a standalone @ApplicationScoped service annotated @Transactional
  on its write method, tests that call the service directly must fetch the entity
  argument (e.g. Team) inside the SAME QuarkusTransaction.requiringNew() block as
  the service call, not in a separate one beforehand. Because the service method carries
  its own @Transactional (TxType.REQUIRED), calling it from a fresh test block starts
  a new persistence context; an entity fetched in an earlier, already-committed transaction
  is detached relative to that new context, which is fragile to pass into a Panache
  entity field assignment (alias.team = detachedTeam) even though it happens to work
  for simple FK-only inserts. In production this never bites because the resource's
  own outer @Transactional method supplies one continuous persistence context from
  fetch through persist -- the bug only surfaces in unit tests that call the extracted
  service directly.

## 1. Objective
Extract TeamResolutionService (LT-008.02) from ParticipationImportResource's inline TeamAlias/AmbiguityReview logic for reuse by the match extraction wizard, with tests calling the service directly instead of through the REST resource

## 2. The Trap
Fetching a Team via Team.findById() in one QuarkusTransaction.requiringNew() block and then passing it into a separately-transactional service method (its own new persistence context) works by accident for simple inserts but is a detached-entity footgun waiting to surface on any future change (e.g. adding a cascade, an eager association read, or an update rather than insert)

## 3. Abstracted Insight
> **Core Principle:** A bean method's own @Transactional boundary is REQUIRED semantics: it joins an already-active transaction if the caller has one, otherwise starts a new one. Test code that wants entity arguments to stay attached across a fetch-then-call sequence must wrap both inside the same QuarkusTransaction.requiringNew() block so they share one persistence context, mirroring how the real caller's outer @Transactional resource method supplies that continuity in production

## 4. Validated Path
Wrap 'Team team = Team.findById(id); service.recordAlias(..., team);' together inside a single QuarkusTransaction.requiringNew().run(...) call in tests that exercise an extracted @Transactional service directly, rather than fetching the entity in setup() and reusing it across multiple later transactional calls
