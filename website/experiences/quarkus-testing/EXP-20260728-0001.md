## 1. Objective
Add ScheduledExtractionJobTest covering a new CompetitionExtractionConfig table (1:1 FK to Competition, no ON DELETE CASCADE) across 4 competition/config/participation combinations

## 2. The Trap
One of four setup branches (configuredOnly) persisted a CompetitionExtractionConfig row but its id was never assigned to a field; cleanup deleted only the two configs whose ids it had, then TeamFormationFixtures.delete() tried to delete all four competitions and hit a FK violation on the untracked one -- which also meant that test's rows leaked into the next test method, making an unrelated assertion fail with double the expected count.

## 3. Abstracted Insight
> **Core Principle:** In a multi-branch fixture setup, every persisted row that appears in ANY branch must have its id captured into a variable cleanup() actually deletes -- 'symmetric' setup/cleanup coverage has to be verified branch-by-branch, not assumed from the last branch written, since it's easy to add one more setup branch (a 4th competition) without updating the id-tracking right alongside it.

## 4. Validated Path
For every new entity persisted in setup(), grep the same setup() method for how many times that entity type's create-call appears versus how many corresponding id fields exist and get deleted in cleanup() -- a mismatch in count is the bug, before ever running the test.

## 5. Verification Checklist
- [ ] Run the new test class alone first (mvn test -Dtest=ClassName) to catch FK violations/leakage before folding into the full suite
