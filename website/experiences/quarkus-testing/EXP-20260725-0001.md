## 1. Objective
Assert the correct HTTP status code on a POST/DELETE resource test where the resource method returns `Response.seeOther(URI)` on success.

## 2. The Trap
REST Assured follows redirects by default, so a test hitting a POST/DELETE endpoint transparently follows the 303 and lands on the final GET response — asserting `statusCode(303)` then fails because the observed status is whatever the redirect target returned (often 200), not 303. It's also easy to mistakenly assert `302` since that's the more common redirect code, but `Response.seeOther(URI)` returns **303**, not 302.

## 3. Abstracted Insight
> **Core Principle:** Any REST Assured call against an endpoint that redirects must chain `.redirects().follow(false)` before asserting the status code, and `Response.seeOther` must be asserted as `303`, not `302`.

## 4. Validated Path
```java
given()
    .contentType(ContentType.URLENCODED)
    .formParam("name", "Levski")
    .when()
    .post("/teams")
    .then()
    .redirects().follow(false)
    .statusCode(303);
```

## 5. Verification Checklist
- [ ] `.redirects().follow(false)` is present on every POST/DELETE assertion that expects a redirect status.
- [ ] `Response.seeOther(...)` endpoints are asserted with `statusCode(303)`, never `302`.
