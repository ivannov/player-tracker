## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
New admin-only /inbox screen (Qute + HTMX) built on LT-009.02's endpoints: lists pending ambiguity reviews with their ranked candidate players, lets the admin pick a candidate or confirm a brand-new player per row, mirroring the resource+template pairing style of MatchExtractionResource but as a single list+action view rather than a multi-step wizard. Linked from templates/tags/appNav.html and 'surfaced prominently right after an admin logs in' per the epic description -- e.g. a pending-count badge near the username/logout control, not buried in a dropdown.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Implemented the ambiguity inbox UI on top of LT-009.02's AmbiguityInboxService.

Design change from LT-009.02: converted InboxResource from a JSON API to Qute HTML/HTMX,
since AC #2 explicitly requires resolving "without a full page reload (HTMX)" -- HTMX swaps
HTML fragments, not JSON, and nothing else ever consumed the JSON contract. Confirmed this
pivot with the user first. Removed the now-unused quarkus-rest-jackson dependency.

- GET /inbox (RolesAllowed ADMIN): full page (InboxResource/page.html) listing pending reviews
  with ranked candidates as buttons + a "confirm as new player" button, mirroring the
  resource+template pairing style of MatchExtractionResource.
- POST /inbox/{id}/resolve and /inbox/{id}/confirm-new: each returns the whole updated
  #inbox-list fragment (InboxResource/list.html), matching the app's established
  "swap the whole panel" HTMX idiom (hx-target="#inbox-list" hx-swap="outerHTML") rather than
  per-row swaps -- list.html is dual-use, {#include}'d from page.html for first paint and
  returned standalone for the HTMX follow-up, same pattern as
  ParticipationImportResource/formationsSelect.html.
- GET /inbox/badge (not ADMIN-restricted, @Authenticated only): small self-fetching HTMX
  island in appNav.html (hx-get, hx-trigger="load", hx-swap="outerHTML") that renders a
  "Неясноти (N)" badge/link next to the username for admins, and an empty fragment for
  non-admins/pending-count-zero -- avoids 403 noise since the badge auto-fetches on every
  page load for every logged-in user (mirrors how the rest of appNav's admin-oriented links
  are already shown to all authenticated users regardless of role, relying on the target
  resource's own @RolesAllowed for enforcement). No isAdmin param added to appNav's own
  signature/call sites -- out of scope for this task, would've meant touching ~15 templates.
  AmbiguityInboxService gained a small countPending() method for this.
- Manually verified end-to-end in a running dev instance (Chrome): logged in as admin, saw
  the "Неясноти (1)" badge appear right after login, opened /inbox, resolved one review by
  picking a ranked candidate (row disappeared via HTMX, no page reload, ambiguity_reviews
  RESOLVED + player_aliases row written -- confirmed via psql), and confirmed a second review
  as a brand-new player (same HTMX no-reload behavior, new players row + alias written).
- Tests: rewrote InboxResourceTest for HTML assertions (was JSON), added badge endpoint tests
  (admin-with-count, admin-zero-count hides link, non-admin gets empty fragment without
  calling the service), added AmbiguityInboxServiceTest.countPendingReflectsOnlyPendingReviews.
  Full mvn verify passes (214 tests).
