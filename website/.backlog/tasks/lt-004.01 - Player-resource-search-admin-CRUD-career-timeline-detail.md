## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
New resource/PlayerResource.java + templates/PlayerResource/{list,form,detail}.html. Player entity (model/Player.java) only has 'names' today -- keep the form to that field, this task does not add new Player attributes. ## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
PlayerResource (/players): public GET list with ?q= substring search (case-insensitive) over
names; public GET /{id} detail rendering a career timeline via a single JOIN FETCH query
(PlayerAppearance -> match, participation, participation.teamFormation.team,
participation.competition), ordered by match date, paired in Java with a batch-loaded map of
MatchEvents per appearance (goals/cards) -- avoids N+1 without adding a matchEvents collection
to PlayerAppearance. /new, /{id}/edit, POST create/update are @RolesAllowed("ADMIN"); list/detail
have no class-level security annotation (public-read/admin-write pattern). Added a "Играчи" link
to appNav.html. Added MatchEventType.getDisplayLabel() (Bulgarian labels) for rendering event
types in the timeline, mirroring FormationType's displayLabel pattern.

Depended on LT-010 (team-side attribution) being implemented first, since the join path needs
PlayerAppearance.participation -- see LT-010's implementation notes.

Tests: PlayerResourceTest (17 tests) cover public list/detail, admin-only enforcement on
new/edit/create/update, search filtering, 404 on unknown player, and timeline correctness with a
multi-team/multi-season/multi-event fixture (verifies chronological ordering and that team,
competition, season and event labels all render correctly).
<!-- SECTION:NOTES:END -->
