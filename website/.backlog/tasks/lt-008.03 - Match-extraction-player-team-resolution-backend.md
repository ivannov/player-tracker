## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Backend service (reusable by LT-009's scheduled job later) that, given a competition (or all) + date: runs fixture discovery, for each match tries the bfu-tournaments.com adapter first and falls back to the ebfu.net adapter (lineups only) when the primary has nothing, resolves each side's team via the shared team-resolution service, resolves every scraped player name via PlayerMatchingService.resolve(rawName, teamId, source) -- confidently-resolved rows collected for admin confirmation, ambiguous rows written to AmbiguityReview with match populated (see LT-010's Participation-based side derivation) -- and on confirm persists Match/PlayerAppearance/MatchEvent rows, guarding against duplicate re-import via the existing (player_id, match_id) unique constraint.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Added com.nosoftskills.lineup.extraction package: MatchExtractionService.preview(ExtractionRequest)/confirm(ExtractionRequest) plus supporting records (ExtractionRequest, TeamSideResolution, PlayerRowResolution, MatchExtractionRow, MatchExtractionSummary). ExtractionRequest takes an explicit fixturesUrl (the bfu-tournaments.com league results page) + competitionId + season + date, mirroring how ParticipationImportResource already takes an explicit URL rather than deriving one from Competition -- no schema change needed; LT-008.04/LT-009 supply this per competition. Per fixture: BfuMatchScraperService tried first, EbfuMatchLineupScraperService (lineups only) as fallback on BfuScraperException, each fixture's failure isolated so one bad match page doesn't abort the whole day. Team sides resolved via TeamAlias-or-name-fallback then Participation lookup (competition+season); confirm() only calls TeamResolutionService.recordAlias for fully-resolvable rows, matching the existing wizard's preview-vs-save split. Every lineup entry resolved via PlayerMatchingService.resolve as literally specified by the task -- this writes PlayerAlias/AmbiguityReview rows even during preview() as that service's own learn-on-read side effect, which is a deliberate, documented exception to preview()'s 'no persistence' promise (scoped only to Match/PlayerAppearance/MatchEvent). confirm() is idempotent: Match reused by (homeParticipation,awayParticipation,date), PlayerAppearance reused by (player,match) pre-check before insert (avoids ever hitting the DB unique constraint), MatchEvent deduped by (playerAppearance,type,minute) since match_events has no unique constraint of its own. Ambiguous players' pending AmbiguityReview gets its match field set once a Match is actually persisted (never during preview, since no Match exists yet). New MatchExtractionServiceTest (6 cases: confident+ambiguous preview without persistence, confirm persists match/appearance/event and links ambiguity to match, idempotent re-run, ebfu.net fallback, both-sources-fail skip, unresolved-team skip) using @InjectMock on the three scraper services. Full mvn verify: 176 tests, 0 failures. Recorded EXP-20260727-0001 (quarkus-hibernate): never mix deleteById() with bulk .delete() across FK-related tables in one transaction -- caused flaky FK-violation failures in this test's cleanup.
