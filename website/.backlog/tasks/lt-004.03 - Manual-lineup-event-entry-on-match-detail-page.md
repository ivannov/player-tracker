## Description

Extends the match detail page from LT-004.02 with an admin-only editing panel wired to PlayerAppearance and MatchEvent (from LT-003: model/MatchEvent.java, model/MatchEventType.java). ## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Extended MatchResource (/matches/{id}) rather than a new resource, since it's the same detail
page: five new ADMIN-only endpoints -- POST .../appearances (add), DELETE
.../appearances/{id} (remove), POST .../appearances/{id}/substitution (set in/out minutes),
POST .../appearances/{id}/events (add event), DELETE .../events/{id} (remove event). detail()
now also loads PlayerAppearances (JOIN FETCH player+participation) and MatchEvents (batched by
appearance id, same grouping-map pattern as PlayerResource's career timeline), splits them into
home/away AppearanceRow lists by comparing participation.id against match.homeTeam.id.

Reused the exact search/create-inline pattern from ParticipationImportResource's team picker
(step2.html) for players: a text input + datalist of existing players resolving to a hidden
playerId via JS, with a "+ Нов играч" toggle swapping to a name-only field that creates the
Player inline server-side. Reused the existing hx-delete + hx-confirm + hx-target="closest
tr"/"closest span" + hx-swap="outerHTML" delete-row convention (same as Team/Competition/
Participation lists) for removing appearances and events -- 204 No Content response, consistent
with every other delete endpoint in the app.

detail.html and the new lineupTable.html partial render the same lineup/event/substitution data
for everyone; admin-only forms (add appearance, add/remove event, edit substitution, remove
appearance) are gated behind {#if isAdmin}, satisfying AC #5's public-read/admin-write split on
a single template rather than two.

Validation is minimal by design, matching this project's existing convention (HTML5 required
attributes + a few explicit BadRequestException checks for the business rules that actually
matter): participationId must be one of the match's two sides, a player can't get two
appearances in the same match (the existing DB unique constraint on (player_id, match_id) is the
backstop but the resource checks first for a clean 400 instead of a raw constraint-violation
500). Substituted-out > substituted-in is enforced only by the existing DB CHECK constraint (no
extra server-side validation) -- consistent with how the rest of the app leaves DB constraints as
the safety net for input the admin is trusted not to garble.

UI note: lineups are stacked vertically (not side-by-side) -- a side-by-side 1fr/1fr grid caused
the away column's wide per-row content (event badges + inline add-event form + substitution
inputs) to overflow the viewport uncontrolled. Caught by browser-testing the live page, not by
the automated tests (which only assert on response bodies, not rendered layout).

Tests: MatchResourceTest grew from 15 to 29 methods, adding coverage for add/remove appearance
(existing player, inline-created player, duplicate-player rejection, wrong-side-participation
rejection), add/remove event, substitution minute updates, and admin-only enforcement (302
anonymous / 403 USER) on every new endpoint.

Verified end-to-end in a live browser session (dev server + admin login): added a goal/red-card
event, set a substitution minute, added a brand-new player inline to the away side, then
confirmed removal of both an appearance and an event via authenticated curl calls (avoided
clicking the hx-confirm delete links directly in the browser, since htmx's hx-confirm triggers a
native window.confirm() dialog that would block browser automation) and reloaded to see the
change reflected. Also confirmed the anonymous/public view renders the same data with zero admin
controls (no hx-delete, no forms, no /matches/new link).
