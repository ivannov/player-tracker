## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Layers local AI embeddings on top of the trigram matching from LT-005.02, per the user's explicit choice to include this from the start rather than as a later enhancement. New OllamaEmbeddingClient in the matching package, using the already-present-but-unused quarkus-rest-client dependency in pom.xml. Embedding population runs asynchronously (e.g. on player creation and via a catch-up pass for existing players) so it never sits on the request path of an admin action. The fallback-to-trigram behavior when Ollama is down is a hard requirement -- this must never become a single point of failure for basic name resolution.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
docker-compose.yml gains an ollama service (ollama/ollama:latest, port 11434, ollama-data volume); README.md documents nomic-embed-text (768 dims, matches players.name_embedding vector(768)) and the pull command. Added quarkus-rest-client-jackson to pom.xml (needed for JSON (de)serialization on the REST client -- quarkus-rest-client alone has no JSON provider). OllamaEmbeddingClient (com.nosoftskills.lineup.matching) wraps a @RegisterRestClient OllamaRestApi hitting POST /api/embeddings; uses CONSTRUCTOR injection (a deliberate one-off deviation from this codebase's usual field-injection style) so tests can build it directly against a throwaway JDK HttpServer without needing Quarkus config-profile gymnastics -- see OllamaEmbeddingClientTest. It never throws: any RuntimeException (connection refused, timeout, bad JSON) is caught and logged, returning Optional.empty() so callers fall back to trigram-only matching. PlayerEmbeddingSyncJob is a @Scheduled(every="1m") catch-up pass over players with name_embedding IS NULL (batch 25) -- chosen over a separate on-player-creation hook per the task's 'e.g.' wording, since the catch-up pass alone already covers both new and pre-existing players without adding a second code path; kept off the request path entirely. PlayerMatchingService.resolve() now re-ranks the trigram candidate pool via cosine similarity (1 - <=> operator) against name_embedding when Ollama answers and at least one candidate has an embedding; otherwise the trigram ranking passes through untouched. Neither the sync job nor the matching service maps name_embedding on the Player JPA entity -- there's no reliable Hibernate 7 + PostgreSQL pgvector column-type binding without the pgvector-java library, so both read/write it via native SQL with a CAST(? AS vector) literal (PgVector.toLiteral), consistent with the pg_trgm native-query pattern already established in LT-005.02. Added %test.quarkus.scheduler.enabled=false so the catch-up job doesn't fire nondeterministically during other tests' fixtures; tests invoke PlayerEmbeddingSyncJob.syncMissingEmbeddings() directly. mvn verify: 137/137 tests pass.
