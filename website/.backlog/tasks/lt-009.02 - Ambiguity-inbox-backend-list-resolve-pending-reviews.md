## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
New service/resource to power the admin ambiguity inbox: list PENDING AmbiguityReview rows with their ranked AmbiguityCandidate players (ordered by score desc), and a resolve action. Refactor PlayerMatchingService.writeAlias(...) from private to a reusable public entry point, then add a public resolveReview(Long reviewId, Long chosenPlayerId) (picks an existing candidate/player) and a 'confirm as new player' variant (creates a new Player, then aliases it) -- both write into player_aliases exactly like the wizard's confirm path, and both update the AmbiguityReview row (status=RESOLVED, resolvedPlayer, resolvedAt, resolvedBy from CurrentUser). New InboxResource (@RolesAllowed("ADMIN") for all endpoints -- this is an admin-only screen per the epic description, unlike the public-read/admin-write pattern used elsewhere) exposing list + resolve endpoints for the LT-009.03 UI to call.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Implemented AmbiguityInboxService + InboxResource (new com.nosoftskills.lineup.inbox package):
- Added source column (ExternalRefSource) to ambiguity_reviews (V1 migration + entity field) -- it was missing, so PlayerMatchingService.queueForReview/TeamResolutionService.queueAmbiguityReview now persist it (only when creating a new review, not when reusing a pending one).
- PlayerMatchingService.writeAlias made public (was private) and reused directly by the inbox service.
- AmbiguityInboxService.listPending(): JOIN FETCH reviews+team, batches candidates in one extra query (no N+1), returns ReviewView/CandidateView DTOs sorted by score desc.
- resolveReview(reviewId, chosenPlayerId): single @Transactional method (existing player is already committed, mirrors PlayerMatchingService.resolve()'s own pattern).
- confirmNewPlayer(reviewId): NOT a single @Transactional method -- creates+commits the new Player in its own QuarkusTransaction.requiringNew() block first, then calls writeAlias (which opens its own separate REQUIRES_NEW transaction internally), then marks the review resolved in a final block. Required because a REQUIRES_NEW-based FK writer can't see a row that's only persisted (not yet committed) in the caller's still-open ambient transaction -- recorded as EXP-20260729-0001.
- InboxResource: JSON REST API (added quarkus-rest-jackson dependency -- no prior JSON precedent existed in this codebase, confirmed this design choice with the user first). @RolesAllowed("ADMIN") on every endpoint per the epic's admin-only-screen note. GET /inbox, POST /inbox/{id}/resolve (form playerId), POST /inbox/{id}/confirm-new.
- No Qute template / nav link added -- deliberately deferred to LT-009.03 per the subtask split.
- Tests: AmbiguityInboxServiceTest (real service + QuarkusTransaction.requiringNew, mirrors PlayerMatchingServiceTest fixtures), InboxResourceTest (@InjectMock service + REST Assured + @TestSecurity, mirrors MatchExtractionResourceTest). Full mvn verify passes.
