## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
MatchResource (/matches): public GET list filterable by ?competitionId= and ?date= (four explicit
query branches rather than dynamic JPQL building, for readability); public GET /{id} detail
showing score, date, and both sides' team/formation/competition/season via a JOIN FETCH query
(homeTeam+teamFormation+team+competition, awayTeam+teamFormation+team+competition -- shared
constant DETAIL_FETCH_JOINS reused by list and detail). GET /new and POST create are
@RolesAllowed("ADMIN"); the new-match form offers two participation pickers (all Participations,
labeled "Team Formation — Competition — Season") rather than a cascading competition/season->team
picker, keeping the UI simple; server-side validation enforces homeTeam != awayTeam and that both
share the same competition+season, re-rendering the form with a 422 and a Bulgarian error message
on violation (this is the concrete implementation of AC #3's "scoped to the same competition and
season"). No edit/update/delete -- out of scope per the task description and AC (LT-004.03 owns
lineup/event editing; score correction after creation isn't mentioned by any AC and was left out
to avoid scope creep). Added a "Мачове" link to appNav.html.

Discovered along the way: Panache's deleteById() loads the entity via findById() then calls
session.remove() -- it is NOT a bulk delete. Chaining several deleteById() calls across related
entities (Team/TeamFormation) in one test-cleanup transaction, followed by an explicit
EntityManager.flush() (as TeamFormationFixtures.delete() does), tripped Hibernate's
checkForTransientReferences validation. Fixed by using Panache's bulk EntityClass.delete("id",
value) instead (proper single DELETE query, no entity loading) -- matches the pattern
TeamFormationFixtures.delete() already used for Participation/TeamFormation. Worth remembering
for any future test that deletes multiple related entities manually in one transaction.

Tests: MatchResourceTest (15 tests) cover public list/detail, competition/date filtering,
admin-only enforcement on /new and create, successful create with and without score, and the two
validation-rejection paths (same participation both sides; mismatched competition/season).

Verified end-to-end in a live browser session (dev server + admin login): created a match via the
form, confirmed the picker labels, scoreboard rendering, list filtering, and that anonymous
requests see the data but no admin controls.
